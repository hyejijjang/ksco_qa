
## 판정 기준

## 4. G0 — Task Revision & Regenerate (모든 기존 Task 신규 평가)

**입력:** 원본 G열 `original_task`, 직무정보 I열, P0에서 확인된 Deliverable Files 핵심 구성, 연결된 경우 실제 Reference Files.

### 4.1 평가 차원

1. `job_fit`: 해당 직업이 수행할 수 있는 업무인가?
2. `deliverable_fit`: Deliverable Files의 목적·필수 표/섹션·파일 형식과 결과가 부합하는가?
3. `grounding`: 근거 없는 결과항목·기간·기관·업무 규칙을 추가하지 않았는가?
4. `input_contract`: 최종 Agent에 제공될 Reference Files의 최소 종류·필드를 설명할 수 있는가?
5. `reasoning_validity`: 실제 필요한 집계·계산·대조·규정 적용·판단 규칙을 식별할 수 있는가?
6. `reconstructability`: 합리적인 입력을 전제할 때 출력의 핵심 구조를 생성할 수 있는가?
7. `output_specification`: 출력 형식 및 확인 가능한 구조가 충분한가?
8. `no_answer_leakage`: 정답 수치·결론이 유출되지 않는가?
9. `no_external_search`: 최종 Agent에게 외부 정보 검색을 요구하지 않는가?
10. `reference_burden`: 향후 Reference 준비 규모/난이도를 설명하고 실현 가능한가?

### 4.2 판정 및 작업

- `KEEP`: 기존 Task가 필수 조건을 충족하고, 바꾸더라도 문체 변경 정도의 이득만 있음. **원본 G열을 effective_task로 그대로 사용**.
- `REGENERATE`: 원본 Task에 확인된 결함이 있고, Deliverable Files 및 직무정보 근거로 개선 가능. **이번 실행에서 새 Task를 실제 작성**하고, 기존 대비 무엇을 왜 고쳤는지 기록. `effective_task=regenerated_task_new`.
- `REVIEW_B`: Deliverable의 핵심 구조 또는 필수 근거를 확인할 수 없어서 채택/수정을 확정할 수 없음. `effective_task=null`.
- `RESELECT_B`: 연결된 Deliverable 자체가 해당 직업·Task의 유효한 결과물로 보기 어렵고 문장 수정으로 해결되지 않음. `effective_task=null`.

**Regenerate 작성 원칙:** Input의 유형/필드, 수행 행위, 반드시 적용할 판단·계산 기준, 산출물의 파일 형식·핵심 구성 명시. 없는 사건/수치/규정을 창작하지 않는다. 미래 Scenario를 대신 만들지 않는다. 1개 셀에 들어가는 한 줄 문자열로 저장. 기존 Task가 충분하면 재생성을 억지로 강제하지 않는다.

### 6.4 16개 품질 지표 (판정 값)

각 지표는 `PASS|REVIEW|FAIL|N_A`로 판정하고 **근거·기준·결론**을 작성한다. 위반이 중대하고 근거가 명확하면 `verify_status=FAIL`, 핵심 정보 부족·중요 결정 필요면 REVIEW, 업무 논리가 충족되고 치명적 모순이 없으면 PASS. 단순 D1/작업 단계가 적다는 이유만으로 FAIL 금지.



## 행 단위 지시

### 입력
이번 호출의 입력은 Task 1개 행의 row_card(JSON)뿐이다. 다른 행은 볼 수 없으며, 다른 행이나 다른 직업을 추정해 판단하지 않는다.
판정 기준의 열 표기는 row_card 필드와 다음과 같이 대응한다.
- 원본 G열 → original_task
- 직무정보 I열 → jobinfo
- Deliverable Files 핵심 구성 → file_profile (P0가 실제 파일을 읽어 만든 구조 요약)
- Deliverable Files 원본 전문 → file_fulltext (있을 때만. 원본 글자를 순서대로 뽑은 것이며 [pN]은 쪽, [시트]·[표k R×C]·[슬라이드 N]은 위치 표시. 붙지 않은 파일과 사유는 file_fulltext_note)
- Reference Files → reference_mode, reference_note (실제 Reference 파일 내용은 제공되지 않는다)
- 직업 → job(전체 경로), job_leaf(평가 대상 직업명)

### 판정 순서
1. job_leaf와 jobinfo를 기준으로 이 직업의 직무 범위를 확인한다. 상위 분류명이나 다른 직업의 기준으로 판단하지 않는다.
2. file_profile(file_fulltext가 있으면 그 원문도)로 Deliverable의 목적·필수 표/섹션·형식을 확인한다. 둘 다에 없는 내용은 확인된 것으로 쓰지 않는다.
3. 10개 차원을 각각 P / R / F / NA로 판정한다. P·R·F·NA는 위 6.4 문장의 PASS·REVIEW·FAIL·N_A에 대응한다.
4. 4.2 기준과 아래 해석 규칙에 따라 action을 하나 고른다.

### 출력 규칙
- job_evaluated: row_card의 job_leaf를 그대로 쓴다.
- checks: 10개 차원 모두 값이 있어야 한다.
- issues: R 또는 F인 차원에만 쓴다. 차원마다 그 차원에 해당하는 구체적 문제를 다른 문장으로 쓰고, 관찰 위치(시트·행·페이지·열 이름 등)를 포함한다. 같은 문장을 여러 차원에 복사하지 않는다.
- 하나 이상의 차원이 F이면 action은 KEEP일 수 없다.
- file_profile·file_fulltext로 핵심 구조를 확인할 수 없으면 REVIEW_B를 쓴다.
- REGENERATE이면 regenerated_task_new에 새 Task를 한 줄로 쓴다. 원본과 같아서는 안 되며, 무엇을 왜 고쳤는지는 reason에 쓴다.
- REGENERATE 작성 금지 조건:
  - 원본 Task의 핵심 처리·판단(집계, 비교, 분류, 계산 등)을 없애거나 단순 복사·보존 작업으로 바꾸지 않는다.
  - 산출물 파일명, 인코딩, 구분자 등 Deliverable 파일 고유 정보를 새 Task에 넣지 않는다.
  - original_task·jobinfo·file_profile에 없는 입력 자료(예: "채권 원장", "승인된 정책 근거자료")를 만들어 넣지 않는다. 입력은 "제공된 자료" 수준으로만 쓰고, 구체적인 종류는 expected_reference_spec에 쓴다.
- KEEP 또는 REGENERATE이면 task_card(input, operations, criteria, output)를 effective_task 기준으로 쓴다.
- reason: 판정 이유를 이 행의 직업명과 관찰 위치를 넣어 구체적으로 쓴다. 다른 행에도 그대로 쓸 수 있는 일반 문장은 쓰지 않는다.
- evidence_loc: 판단 근거가 된 file_profile 또는 file_fulltext 안의 위치를 적는다.
- expected_reference_spec: 최종 Agent에 제공될 Reference의 최소 종류·필드를 적는다.
- file_profile·file_fulltext·jobinfo·original_task에 없는 수치·기관명·기간·규정을 만들어 넣지 않는다.
