## 판정 기준
## 6. G2 — Task Design Verification (Reference 두 가지 Case)

G2는 **Task 자체 설계의 품질 검수**다. 미래 AI실이 Scenario·Reference Files·Rubric을 만들 수 있는가를 판단하며, 실물 생성은 하지 않는다. G0 자기평가를 그대로 복사해서는 안 된다. 가능하면 다른 평가 컨텍스트를 사용한다.

### 6.1 Reference Files가 **없는** 경우

`reference_mode=GENERATE_REFERENCE`. Deliverable Files에서 확인된 필수 결과를 출발점으로, 미래 AI실이 다음을 설계할 수 있는지 검증한다.

- Scenario: 현실적 업무 맥락·요청 목적·대상 범위·제약을 구성할 수 있는가?
- Reference 설계: 필요한 파일 종류, 최소 필드, 자료 단위, 기간·분류·규칙, 예외 조건을 정의할 수 있는가?
- Reasoning: 입력 → 처리/판단 → Deliverable 핵심 출력의 논리 연결이 가능한가?
- Evaluation: 이후 생성된 Reference/Scenario로 수행 결과를 Deliverable과 객관적으로 비교할 수 있는가?

**실물 Reference 없음 = 자동 REVIEW/FAIL이 아니다.** 미래 Reference를 생성했다고 주장하지 않는다. 입력 자료가 B에서 유일하게 역산되지 않아도 일관된 생성 설계가 가능하면 PASS 가능하다.

### 6.2 Reference Files가 **있는** 경우

`reference_mode=PROVIDED_REFERENCE`. 실제 원본을 열어 관련 시트·필드·단위·기간·규칙을 확인한다. `Reference → Task 처리·판단 → Deliverable 핵심 결과`를 연결한다.

- 충분하면 `reference_action=REUSE`, `reference_readiness=READY_AS_IS`.
- 부족하지만 생성·정제·필드 보완으로 가능한 경우 `reference_action=SUPPLEMENT|ADAPT`, `reference_readiness=READY_WITH_ACTION`, 부족 필드와 보완·검증 방법 명시.
- 심각한 구조 충돌이나 정답 누출은 `CONFLICT`로 표시하고 보완 가능성을 따로 판단한다. **Reference 자체의 보완 필요 ≠ Task FAIL**. 실제 Reference로 완전한 최종 정답을 재현했다고 주장하지 않는다.
- 제공 선언은 있는데 못 찾는 경우 `UNRESOLVED_REFERENCE`, `reference_readiness=HOLD`, 최종 REVIEW가 기본값.

### 6.3 핵심 Deliverable 확인 수준

- `SUFFICIENT`: Task 관련 핵심 출력 구성·축·기준을 확인.
- `PARTIAL_NONCRITICAL`: 일부 미열람 부분이 필수 출력과 무관함을 설명 가능.
- `PARTIAL_CRITICAL`: 중요한 항목/판단 규칙 미확인, 해당 항목 REVIEW.
- `MISSING`: 파일 누락/열람 불가/유효 증거 전무, B 정합성 PASS 금지.

### 6.4 16개 품질 지표

`job_fit`, `deliverable_fit`, `grounding`, `input_contract`, `reasoning_requirement`, `reconstructability`, `answer_leakage`, `no_external_search`, `reference_burden`, `output_specification`, `task_clarity`, `agentic_value`, `difficulty_fit`, `scenario_feasibility`, `reference_design_feasibility`, `evaluation_alignment`.

각 지표는 `PASS|REVIEW|FAIL|N_A`로 판정하고 **근거·기준·결론**을 작성한다. 위반이 중대하고 근거가 명확하면 `verify_status=FAIL`, 핵심 정보 부족·중요 결정 필요면 REVIEW, 업무 논리가 충족되고 치명적 모순이 없으면 PASS. 단순 D1/작업 단계가 적다는 이유만으로 FAIL 금지.

### 6.5 AI실 인계용 청사진 (실물 생성 금지)

- `scenario_blueprint`: 업무 맥락, 요청 목적, 대상 범위, 추후 설정해야 할 조건.
- `reference_blueprint`: Reference 파일 종류, 실존/예상 구분, 최소 필드, 규칙·자료 규모, 생성/재사용/보완 방법.
- `reasoning_map`: 입력 필드 → 추출·계산·분류·대조·판단 → Deliverable 핵심 결과의 연결.
- `evaluation_blueprint`: 평가 가능한 항목, 검산·문서 구조 대조 등 검증 방식, 정답 누출 방지.



## 행 단위 지시

### 입력
이번 호출의 입력은 Task 1개 행의 row_card(JSON)와 effective_task뿐이다. 다른 행은 볼 수 없으며, 다른 행이나 다른 직업을 추정해 판단하지 않는다.
- 직업 → job(전체 경로), job_leaf(평가 대상 직업명), jobinfo(직무정보)
- Deliverable Files 핵심 구성 → file_profile (실제 파일을 읽어 만든 구조 요약)
- Reference Files → reference_mode, reference_note. 실제 Reference 파일 내용은 제공되지 않는다.
- 평가 대상 Task → effective_task (원본 Task는 original_task)
이 행은 이미 G2 평가 대상으로 선별되었다. SKIPPED를 판정하지 않는다.

### 판정 규칙
- 지표 값은 P(=PASS), R(=REVIEW), F(=FAIL), NA(=N_A)로 쓴다.
- 지표의 기준 문장은 쓰지 않는다. 기준은 고정되어 있다.
- R 또는 F인 지표는 issues에 그 지표에 해당하는 구체적 문제를 다른 문장으로 쓰고, 관찰 위치를 포함한다. 같은 문장을 여러 지표에 복사하지 않는다.
- 하나 이상의 지표가 F이면 verify_status는 PASS일 수 없다.
- b_coverage_status는 file_profile로 실제 확인한 범위만 기준으로 정한다. file_profile에 없는 부분을 확인한 것으로 쓰지 않는다.
- reference_mode가 GENERATE_REFERENCE이면 reference_action은 GENERATE다.
- reference_mode가 PROVIDED_REFERENCE 또는 UNRESOLVED_REFERENCE이면, 실제 Reference 내용을 확인하지 못했으므로 내용이 충분하다고 판정하지 않는다. [확인: 이 경우의 reference_action·readiness 기본값]

### 출력 규칙
- blueprints의 scenario, reference, reasoning_map, evaluation은 각각 6.5의 scenario_blueprint, reference_blueprint, reasoning_map, evaluation_blueprint에 해당한다. 실물을 만들지 않고 설계만 쓴다.
- blueprints에는 row_card(effective_task, jobinfo, file_profile)에 없는 수치·기관명·기간·규정을 만들어 넣지 않는다. 추후 정해야 할 값은 "추후 설정"으로 표시한다.
- reason: 이 행의 직업명과 관찰 위치를 넣어 구체적으로 쓴다. 다른 행에도 그대로 쓸 수 있는 일반 문장은 쓰지 않는다.
- evidence_loc: 판단 근거가 된 file_profile 안의 위치를 적는다.
- proposed_fix: verify_status가 REVIEW 또는 FAIL일 때, Task를 어떻게 고치면 되는지 구체적으로 쓴다.

## 겹치는 10개 지표 — AGREE_CHECK

겹치는 10개 지표(job_fit, deliverable_fit, grounding, input_contract, reasoning_requirement, reconstructability, answer_leakage, no_external_search, reference_burden, output_specification)는 행의 G0 action에 따라 다르게 처리한다. overlap_review.mode에는 입력에 표시된 모드를 그대로 쓴다.

### 입력에 G0 판정이 없는 경우 (G0 REGENERATE 행)
- 10개 지표를 effective_task와 row_card만 보고 새로 판정해 overlap_review.checks에 쓴다.
- disagree는 빈 목록으로 둔다.

### 입력에 G0 판정이 있는 경우 (G0 KEEP 행)
- G0 값을 정답으로 보지 않는다. 지표마다 row_card로 직접 근거를 확인한 뒤 동의 여부를 정한다.
- 근거로 뒷받침되면 G0 값과 같은 값을 overlap_review.checks에 쓴다.
- 근거가 G0 값과 다르면 overlap_review.checks에 자신이 판정한 값을 쓰고, disagree에 해당 지표, G0 값, 새 값, 이유를 적는다.
- 근거를 확인하지 않고 G0 값을 그대로 옮기지 않는다.

고유 6개 지표(task_clarity, agentic_value, difficulty_fit, scenario_feasibility, reference_design_feasibility, evaluation_alignment)는 항상 new_checks에 새로 판정한다.

## 겹치는 10개 지표 — FULL_RECHECK

입력에는 G0 판정이 포함되지 않는다.
- 겹치는 10개 지표를 effective_task와 row_card만 보고 새로 판정해 overlap_review.checks에 쓴다. overlap_review.mode에는 입력에 표시된 모드를 그대로 쓰고, disagree는 빈 목록으로 둔다.
- 고유 6개 지표는 new_checks에 판정한다.
